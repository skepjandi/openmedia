# Platform Support

> **Status: Partially implemented.** Native iOS (Swift) and Android (Kotlin) site-view plugins exist. iOS behavior has simulator evidence; Android debug startup and one onboarding tap were verified on one emulator, but broader Android behavior and a signed store build remain unverified. macOS site views exist (debug builds were run on one Mac, see [The macOS site view](#the-macos-site-view)). Windows and Linux site views exist and compile on their targets, but no Windows or Linux machine has run them yet (see [The Windows and Linux site view](#the-windows-and-linux-site-view)).

## The core constraint

Tauri's multi-webview API (`Window::add_child`) is gated behind the `unstable` Cargo feature and **desktop-only**; upstream tracks mobile support in [#11794](https://github.com/tauri-apps/tauri/issues/11794) and [#11528](https://github.com/tauri-apps/tauri/issues/11528), both open. A mobile app has one Tauri webview, and navigating it to a site would destroy the shell. So:

- **Mobile (iOS and Android):** each uses an in-repository native site-view plugin (`tauri-plugin-siteview`), positioned by the shell. The implementation exists on both platforms; iOS is the verified platform.
- **macOS, Windows and Linux:** a Tauri child webview per session (`src-tauri/plugins/tauri-plugin-siteview/src/desktop/`, one module for the three, with what differs per system in `desktop/platform/`). See [The macOS site view](#the-macos-site-view) and [The Windows and Linux site view](#the-windows-and-linux-site-view).

The shell talks to the shared site-view API (`open`, `set_rect`, `navigate`, …); the native iOS and Android plugins and the desktop module implement it ([Architecture](./architecture.md#components)).

**Causes found.** The launch storyboard used the system background (white or black). A new `WKWebView` draws its own white or black until its first frame, and `open` also awaited the WebKit compile of the content rule lists (seconds on the first run) and, in Rust, the list conversion, before the view existed. The shell is transparent, so the window showed through. The splash faded out when state loaded, not when a page existed.

**Fixes.** `SiteViewPlugin` puts a themed backdrop view under every page and keeps a new page at alpha 0 until its first frames are reported (native-only `openmediaPaint` handler, `didFinish`, or 1.5 s after commit), then fades it in. `open` looks lists up in WebKit's store and loads at once; missing lists compile in the background and attach to open pages without a reload (so the very first page after an install or list update is not blocked; its next navigation is). Rust converts the lists at launch. The launch storyboard uses a `LaunchBackground` color (ink / paper). The splash waited for the first page address, at most 4 s; see [Startup](#startup) for what replaced that.

**Not pursued.** Pre-warming a `WKWebView`: a second open took the same 470 ms to commit as the first, so there is no process start to hide. Launch-screen color follows the system appearance, not the in-app theme override.

**Found while testing:** a synchronous Tauri command that calls into the plugin deadlocks the app (it blocks the main thread waiting for native code that needs the main thread). Commands that reach native code must be `async`; see `open_site`.

**Usage controls (iOS):** daily blocking is a native blur shield attached to each affected session. It stops loading, persistently suspends media playback, blocks navigation and touch interaction, and preserves deferred recipe reloads until the session is unblocked. The Rust-only plugin method adds no webview capability. Native Swift compilation and standalone domain checks are automated; physical-device behavior remains unverified.

**Background media.** A page that is hidden behind another page, or any page while the app is in the background, has its media paused unless its site is on the "keep playing" list (`set_background_media`, a Rust-only plugin method; sites are registrable domains). iOS: `setAllMediaPlaybackSuspended` from `refreshMedia()` in `SiteViewPlugin.swift`, driven by `show` and by `didEnterBackground`/`willEnterForeground`. Android: a script that pauses every `video` and `audio` element of the main frame and remembers which it paused, run from `refreshMedia()` in `SiteViewPlugin.kt` on `show` and on the activity's `onPause`/`onResume`; with the app in the background the view itself is also paused (`WebView.onPause`, `setViewPaused`), which reaches iframes and players that start again after the script's pause. macOS: the same script from `apply_media` (`media_step`, tested), when the active session changes or the window is minimized or the app hidden (`follow_window`, read by the poller), followed by `setAllMediaPlaybackSuspended` on the web view (`native::set_media_suspended`, one resume per suspend) so iframes are paused too; a page with a video in a picture-in-picture window is not suspended. iOS: a page left for the background is suspended unless a real picture-in-picture window is up (the page's own small player does not count); a window asked for on leaving is given 0.8 s to appear, a page that does not answer within 0.6 s is suspended, and a window kept open is checked every 2 s in the background (`watchWindows`) so closing it does not leave the page playing. Resuming plays only the elements that were paused. Limits: media inside iframes is not touched on Android and macOS, and an element a page replaces while hidden is not resumed. Not verified on a device or in the simulator: the Swift and Kotlin were compiled (Kotlin with the Gradle `compileDebugKotlin` task, Swift type-checked against the Tauri sources) but not run.

**Covered page.** A new tab, or switching incognito on or off, puts the shell's blank page over the page in front, which stays alive underneath. The shell tells the native side (`set_covered`, shell-only, in the plugin's default permission set; `setCovered` on iOS and Android, `set_covered` on macOS), which then handles that page as one left for another: its media is paused unless its site is on the "keep playing" list. iOS: a page left for another floats in a picture-in-picture window only when its site has the picture-in-picture switch on (`floatScript(for:)`); otherwise it is paused with the page. Android: the pause script also pauses media in same-origin iframes and tells every frame to pause its own (`FRAME_HOLD_SCRIPT`, installed in all frames with the page reporter), because a script reaches only its own document.

**Picture-in-picture (iOS).** Off for every site; a favorite's editor has a switch (`set_site_picture_in_picture`, saved as `pictureInPictureSites` in `library.json`, registrable domains) that reaches `SiteViewPlugin.swift` through the Rust-only plugin method `set_picture_in_picture`. Four pieces: (0) the plugin puts the app's `AVAudioSession` in the playback category when it loads (`.playback`, `.moviePlayback`; only the category, WebKit activates the session when media plays). Without it a web view's video reports no picture-in-picture support and is silenced by the ringer switch, so nothing floated; the simulator reports no picture-in-picture support either way, so this is unverified on hardware; (1) `UIBackgroundModes: [audio]` in `project.yml` and `Info.plist`, which iOS requires before a web view's video may float or keep playing out of the app; (2) a document-start script in every frame, in its own `WKContentWorld` (`pictureInPictureGuardScript`), that sets `disablepictureinpicture` on each `video` unless the top page's host is on the list, so WebKit offers no PiP button elsewhere, and is re-run live when the list changes (frames already loaded take it on their next load); (3) on `willResignActiveNotification` the page in front, if its site is listed, floats its largest playing video that has sound with `webkitSetPresentationMode('picture-in-picture')` (`evaluateJavaScript` supplies the user gesture WebKit requires), and `didBecomeActiveNotification` puts a video floated this way back inline. A listed page that goes to the background keeps its media only while a video is floating (`suspendUnlessFloating`); otherwise it is suspended like any page out of sight. Only the main frame's videos are floated automatically; a player in a frame can still be floated by hand. Android and macOS accept the list and do nothing (Android would need the activity to enter PiP; macOS web views have WebKit's own video control), and the shell shows the switch only on iOS. Not verified on a device or simulator: whether iOS lets the web view start PiP from `willResignActive`, and the background-mode App Store review answer.

**Incognito (iOS):** the biometric check is a Rust-only plugin method (`authenticate` in `SiteViewPlugin.swift`) on `LocalAuthentication`. `.deviceOwnerAuthentication` tries Face ID or Touch ID first and lets the system offer the passcode after failures or when nothing is enrolled; a device with neither fails closed. The Swift code compiles for `aarch64-apple-ios-sim` and the shell flow was exercised in a browser with a mocked `invoke`; the real Face ID prompt has not been run on a simulator or device. Android returns an unsupported error; macOS has its own check, see [The macOS site view](#the-macos-site-view).

**Decisions that follow:**

- **iOS 17 is the minimum.** `forIdentifier:` is iOS 17+, and the Tauri iOS template defaults to 15, so `tauri.conf.json` sets `bundle.iOS.minimumSystemVersion` to 17.0. This resolves the roadmap's open question on older iOS versions.
- Android requires `MULTI_PROFILE` and `WEB_MESSAGE_LISTENER` at runtime; Kotlin implements these checks and has no single-profile fallback. Device/emulator behavior remains unverified.

## Startup

Cold start used to show an empty screen (launch screen), then the splash, then an empty screen again until a heavy page painted. Measured and fixed in `perf/startup-handoff`.

**Causes.** (1) The launch screen was a plain colour and the splash's logo arrived a request later, so the first second showed nothing. (2) The splash left when the page reported an address, which is at commit; a page that commits long before it paints (a script-rendered site) was then hidden at alpha 0 over an empty backdrop. (3) The page was opened only after the shell had booted, rendered, called `get_state`, rendered again and called `open_site`; the page's web process, DNS lookup and request all queued behind that. (4) The first-paint signal fired after two animation frames at document start, which is before any content exists.

**What changed.**

| Area | Change |
|------|--------|
| Launch screen | `LaunchScreen.storyboard` shows the logo (`LaunchLogo` image set, 52% of the width, at most 240 pt: the splash's size and place). `SiteViewPlugin.installBackdrop` keeps the same logo under the shell until the first page is revealed, so the gap between the launch screen and the shell's first paint is not empty either |
| Splash | The logo and the stylesheet are inlined into `index.html` by a Vite plugin (`inlineFirstPaint`), so the splash paints with the first HTML, not after two more requests. It shows the logo exactly where the launch screen puts it (centred, 52% of the width, at most 240 px), a soft halo behind it, the host of the site being opened, and a hairline accent track that follows the launch: `boot` (the web view starting), `shell` (the state loaded) and `done` (the first site on screen). Fade-out is 320 ms |
| Splash to page | The splash stays until the site the app opened at launch has painted, not merely started loading: a page that commits early still shows an empty view until it draws, and that frame is what the splash hides. Native sends `painted` in `siteview:state` when it reveals the view; `splashDone` in `splash.ts` lifts the splash on `painted`, when there is no site to wait for, when the start page could not be opened, or after 12 s |
| First paint | The injected script reports the page's first contentful paint (`PerformanceObserver`, two frames as a fallback) instead of two frames at document start. A view that is not in the window yet never reveals |
| Page opens at launch | `boot.rs`: in `setup`, Core opens the start page (`Library::start_url`: the last page, else the first valid favorite) with `open_session`, before the shell has loaded, and resolves its host so the DNS answer is cached. `get_state` returns the session id (`bootSession`); the shell calls `adopt_boot_session` once its event listeners exist, which sets the real rectangle and re-announces the state it could not hear. If the start page failed to open, the same call opens it as `open_site` would. The native `open` takes an optional rect and may run before the shell's view is in the window: it creates the view and starts loading, then mounts it (`attachShell`) |
| Shell boot | `get_state` is requested before React renders (`prefetchStartup`); `get_state` and the hot commands (`set_last_url`, `add_history`, `record_usage`, `get_sites`, `bottom_margin_for`) run off the main thread; Settings and Stats are separate chunks fetched after the splash is gone, and the guide only when it opens; site options and favicons are fetched after the first page shows. The library file is rewritten at launch only when it was migrated |
| Build | Vite targets Safari 17 and drops the modulepreload polyfill |

**Measured.** iPhone 17 simulator (iOS 26.5), release build, loopback fixture whose response takes 0.3 s and whose content is drawn by script 1.5 s after commit (a stand-in for a script-rendered site). Video from `simctl io recordVideo`, 60 fps; "empty" is a frame whose centre is one flat colour. Baseline (`origin/main`) and this change installed fresh and alternated, three rounds. Another process was filling the disk during the runs, which made the simulator's process starts slow and uneven.

| Metric | Before (3 runs) | After (3 runs) |
|--------|-----------------|----------------|
| Empty frames after the app appears | 2867 / 2033 / 1433 ms | 0 / 0 / 0 ms |
| App appears to page visible | 5.37 / 4.47 / 3.87 s | 2.57 / 4.38 / 3.17 s |

The empty-frame result is clear. The time-to-page spread is wide (one "after" round was slowed by a late app start), so the three-run medians, 4.47 s to 3.17 s, show a direction and no more. What the logs show directly (release build, simulator, ad blocking on): Rust `setup` takes 15 ms; the page view is created and loading 0.17 s after the shell's view exists, where before it waited for the shell's JavaScript, two renders and two commands; the page's first request then leaves 0.6 to 0.9 s later, the same moment the shell's own JavaScript starts, because the simulator needs that long to start each web process (this floor is the simulator's; a device is expected to be shorter, not measured). One run with ad blocking off did not shorten that wait (0.87 s), so the rule lists are not what it is.

**Not measured.** A real device, real sites, dark mode (the launch screen colour follows the system appearance), iPad, and the first launch after an install (Rust still converts the filter lists before the start page opens; unchanged). DNS warm-up is a design effect, not a measured one.

**Not pursued.** Inlining the module script (one request; the cost is parsing, not the fetch); replacing React with a smaller runtime (about 190 KB of the 256 KB main chunk, a rewrite risk for this change); caching the compiled page script and rule-list handles in memory (not on the measured path).

## Layout model (mobile)

The site view is a native view *below* the Tauri shell, so the shell's floating controls draw over the page:

- The shell webview is transparent (`isOpaque = false`, clear backgrounds). The shell reserves a full-screen rectangle inside the safe area and reports it with `set_rect`; the native site view fills it.
- A transparent `TouchRouter` view sits above both. The shell reports the rectangles of its interactive elements (`[data-hit]`) with `set_interactive_regions`; a touch inside one goes to the shell, any other touch goes to the page. With no site view open, the shell gets every touch.
- Opening the fan, the command bar or settings adds a full-screen interactive region, so the page cannot be touched underneath them.
- **Sessions.** The plugin keeps one `WKWebView` per session (a dictionary keyed by the shell's session UUID), all stacked below the shell, all but the active one `isHidden`. `open` adds a view and shows it; `activate` shows an existing one without reloading; `close` removes one. Every session uses the same profile data store, so logins are shared. The touch router points at the active view only. A session's content rule lists are swapped on all views; hidden ones reload when next shown. A backdrop view (the app's ink or paper) sits under every page, and a new page stays invisible until it has painted. Lifetime policy lives in the shell ([UI Design](./ui-design.md#sessions)); the plugin only reports `siteview:memory` (from `UIApplication.didReceiveMemoryWarningNotification`) and `siteview:closed` (a hidden session's web content process died).
- **Domain pinning and the popup.** `decidePolicyFor`, `createWebViewWith` and the first-load rule go through `DomainScope.verdict` (`src-tauri/plugins/tauri-plugin-siteview/ios/Sources/DomainScope.swift`, pure Foundation, checked by `scripts/test-domain-scope.sh`). User-activated top-level links and back/forward history stay in the embedded view, whose domain scope follows redirects until the load settles; automatic off-domain navigation (a sign-in redirect the page makes from script) opens in a window inside the app that shares the profile's data store; when it comes back to the session's domain, the page's own view loads that address and the window closes (`openRedirectWindow`). `SFSafariViewController` is only the fallback when that window cannot be built.
- **The sign-in window.** A window the page opens with `window.open` (Google or Apple sign-in) is a sign-in window, and it opens inside the app: above the page, in the page's own data store, with `window.opener` kept. WebKit hands over the configuration to build it with (`createWebViewWith`), which carries the opener's store and the link to the opener, so the sign-in and the page share one cookie jar and the sign-in can hand its token back. It closes when the page closes it (`webViewDidClose`), when Back is pressed, when its session closes and when another session is shown. Only `http`, `https` and `about:` load in it, and it follows its own redirects: the identity provider and the site it returns to are different domains.
- Native gestures (iOS edge-swipe back and forward, pull to refresh) stay on the site view; state changes are mirrored to the shell via `siteview:state` events. The shell's own full-screen pages get the same back swipe in JavaScript, because iOS gives them none.
- **Back and gesture exclusion (Android).** The system Back button and edge gesture are handled in the shell: `useAndroidBack` registers Tauri's `back-button` listener only while something wants the press (a handler on `backStack`, or a page that can go back and is not closed by a usage limit). Unregistered, the press falls through to the system and leaves the app, so an idle app still exits normally. `setInteractiveRegions` also hands the regions that touch a screen edge and are under 200 dp tall to `setSystemGestureExclusionRects`, so dragging the floating button inward is not taken for Back.
- **Pull to refresh inside a scrolling container (Android).** A feed of full-screen videos scrolls inside a container while the page itself stays at its top, so the refresh layer saw "nothing to scroll" and a swipe down to the previous video pulled to refresh and reloaded the page. A document-start script now reports, at the start of every touch, whether the touch began inside an element scrolled away from its top (`openmediaScroll`, a write-only channel like the paint one), and `SwipeRefreshLayout.setOnChildScrollUpCallback` refuses to refresh while that is true, on top of the WebView's own check. Not verified on a device or emulator.
- **Pull to refresh inside a scrolling container (iOS).** Same script as Android (`touchScrollScript`, handler `openmediaScroll`); on a touch that began inside a scrolled container the `UIRefreshControl` is detached from the scroll view (`Session.refreshControl` keeps it) and re-attached on the next touch that did not. Not verified on a device or simulator.
- **Pull to refresh (Android).** Each page view sits inside a `SwipeRefreshLayout` that the page layer lays out; the touch router dispatches to that frame. The spinner stops on `onPageFinished` or a main-frame error and is disabled while a page is closed for the day.
- Tap-to-pick, AI chat, and the rule list live in the command bar and settings; the picker highlight lives in the page (engine).

Fallback if the native-plugin approach fails: navigate the main webview to the site and inject shell UI as an overlay in the page. Much weaker (shell dies on navigation, UI shares a realm with the hostile page), so treated as a last resort and not planned.

## The Android site view

`src-tauri/plugins/tauri-plugin-siteview/android` (Kotlin, package `surf.openmedia.siteview`, class `SiteViewPlugin`) is the Android twin of the Swift plugin and speaks the same Rust API (`src-tauri/plugins/tauri-plugin-siteview/src/models.rs` is the source of truth; the JSON is camelCase, and `setBlocked`, `authenticate`, `biometryKind` and `evaluate` stay Rust-only).

- **Layout.** Tauri puts the shell webview straight into the activity's content view, so the plugin adds its own `PageLayer` (a `ViewGroup`) as the first child of that content frame: the page views live in the layer, below the shell, and the layer lays them out at the rectangle the shell reports with `set_rect`. The shell is made transparent (`setBackgroundColor(Color.TRANSPARENT)`) so the page shows through it, and a backdrop in the layer holds the app's own colour until a page has painted.
- **Touch routing.** Android has no hit-test fall-through between sibling views, so the shell webview keeps an `OnTouchListener`: a touch inside a region the shell reported goes to the shell, every other touch is copied to the page webview with its coordinates moved into the page's space and dispatched there. DOM rectangles are CSS pixels; the plugin scales them by display density before comparing them with Android's physical-pixel touch coordinates.
- **Safe area.** The Android WebView reports `env(safe-area-inset-*)` as 0 for system bars when the activity is edge-to-edge. The shell therefore uses `--safe-top` / `--safe-bottom` (default `env(...)`, so iOS is unchanged); `SiteViewPlugin.publishSafeArea` overrides them on the root element from `WindowInsetsCompat` (system bars and display cutout, CSS pixels) through a document-start script plus an immediate evaluation, and fires `resize` so `useInsets` re-measures.
- **System bars.** `setColorScheme` (the app's Appearance, for the app's own chrome only: pages never see it) sets the status bar's icon colour (`WindowInsetsControllerCompat.isAppearanceLightStatusBars`) from the app's resolved theme, and `onConfigurationChanged` re-applies it when the scheme is "system" and the device flips. `enableEdgeToEdge()` picks the icons from the device's theme only, so an app set to Dark on a light device got dark icons on the shell's dark strip under the status bar. The navigation bar is left to the system, which already adapts its contrast to what is behind it.
- **Profiles.** `open` refuses to run unless the System WebView reports `MULTI_PROFILE` and `WEB_MESSAGE_LISTENER`, and the page is put in the profile named by the shell's profile id (`WebViewCompat.setProfile`). There is no single-profile fallback: the profile-isolation invariant would break.
- **Document start.** The recipe script and the first-paint reporter go in with `WebViewCompat.addDocumentStartJavaScript`. Without that feature the scripts are injected when the page starts instead, which is late: a CSS-first rule may flash.
- **Bridge.** `WebViewCompat.addWebMessageListener` gives the page a write-only `openmedia` object. Only the main frame's messages are taken, the body must be a JSON object or array, and the message's own origin travels with it. No Tauri IPC reaches a page view.
- **Popups and links.** Automatic navigation outside the session's domain (a sign-in redirect the page makes from script) opens in a window inside the app, in the session's profile; when it returns to the session's domain the session's WebView loads that address and the window closes (`openRedirectWindow`). A Custom Tab is only the fallback when that window cannot be built. A user-activated top-level link, including a search result, stays in the WebView; browser back/forward remains inside its navigation history.
- **Ad popups and redirects (all platforms).** A window the page opens, or an automatic cross-domain redirect after the load settles, is allowed only when the address looks like a sign-in or a payment (`DomainScope.looksLikeSignIn`: a known identity-provider host, an `/oauth`, `/authorize`, `/saml`, `/sso`, `/login` style path, or OAuth/SAML query parameters). Anything else is dropped without a window: popunders and redirect ads go to throwaway domains no list names. Android also refuses `window.open` without a user gesture and closes a popup whose first address is neither the site nor a sign-in; macOS applies the check in `on_new_window` (`looks_like_sign_in`). It is a heuristic: a sign-in from an unknown provider with none of those marks, or a script redirect to another domain that is neither, is refused. It is a sub-setting of Block ads and trackers (`blockPopups` in `library.json`, on by default, in force only while ad blocking is on; each `open` carries it to the native side, so it applies to pages opened afterwards). Each drop emits `siteview:popup-blocked` with the host, and the shell shows a throttled notice (at most one per 30 s) telling the user to switch it off if a sign-in or payment failed. Tested in `scripts/test-domain-scope.sh`, `DomainScopeTest.kt` and the macOS unit test; not yet run on a device.
- **The sign-in window.** A window the page opens with `window.open` (Google or Apple sign-in) opens inside the app, above the page, in the session's own profile (`WebViewCompat.setProfile`), so the sign-in and the page share one cookie jar. Android's WebView gives such a window no `window.opener`, so the plugin adds one: a document-start script gives the window an `opener` whose `postMessage` goes to the app over a write-only `openmediaOpener` channel, and the app hands it to the opening page as a `message` event. The window's first address decides where it belongs: a page of the session's own site is loaded in the session instead, everything else stays in the window. It closes when the page closes it (`onCloseWindow`), when Back is pressed, when its session closes and when another session is shown. Android cannot tell a clicked `target=_blank` link from a scripted `window.open`, so an outside link opens in the window rather than in the session; iOS keeps the clicked link in the session.
- **Blocking.** A closed site is covered by a native shield, its load stops, its timers stop (the closest Android has to suspending media) and every navigation it asks for is refused.
- **Owner check.** `BiometricPrompt` with `BIOMETRIC_WEAK`, plus `DEVICE_CREDENTIAL` on Android 11 and above; a device with neither fails closed.
- **Notifications.** A local notification for a hidden session, with the session id in the intent; the tap is reported back as `siteview:notification-tap`. `POST_NOTIFICATIONS` is requested the first time one is due.
- **Secrets.** Android has no `keyring` backend, so the plugin's Kotlin side keeps a key in the Android Keystore (AES-GCM) and writes only the ciphertext to the app's preferences, which the app's backup rules exclude. Rust reaches it through a Rust-only plugin command, so no webview can ask for a key.

**Build verification.** `yarn tauri android build --aab --ci` produced `src-tauri/gen/android/app/build/outputs/bundle/universalRelease/app-universal-release.aab` (25 MB), with release Rust libraries for all four Android ABIs and compiled Kotlin plugins. The AAB is unsigned because no upload key was configured; `jarsigner -verify` reported it unsigned. Release signing reads the ignored `src-tauri/gen/android/keystore.properties` (`keyAlias`, `password`, `storeFile`) when present. **Emulator smoke:** `yarn tauri android dev "Medium_Phone"` installed and launched `surf.openmedia` on `emulator-5554` (`sdk_gphone64_arm64`); its main activity remained foreground and tapping onboarding's Next control advanced to step 2. This verifies startup and one shell hit target only, not broader Android behavior or physical devices. See [Store Builds](./store-builds.md). Never commit the keystore properties file.

## The macOS site view

`src-tauri/plugins/tauri-plugin-siteview/src/desktop/` (with `platform/macos.rs` and `platform/macos/` for what is Mac-only) implements the shared site-view API with Tauri child webviews (`Window::add_child`, which needs Tauri's `unstable` feature and is desktop-only).

**Layout.** The model is mobile's: the page views sit under a transparent shell, and the floating button, fan, command bar and sheets draw over the page. A web view added later goes on top of its siblings, and Tauri has no z-order call, so `shell.rs` does three things natively with the shell's own `WKWebView`: it stops painting a background (the private `drawsBackground` key, the same one Tauri's `macOSPrivateApi` sets), re-adds the view above the page views after each is created, and replaces `hitTest:` on its class so a click is offered to the shell only inside the interactive regions the shell reports (`set_interactive_regions`) and to the page view underneath everywhere else. It is the macOS counterpart of the iOS `TouchRouter`. The shell reports the page's rectangle in its own coordinates (`set_rect`); the plugin places the page relative to the shell's content area (its web view reaches under the title bar, so its `safeAreaInsets` are added). While an overlay is open (a region covering most of the page) the keyboard goes to the shell, otherwise to the page. The window opens at 1100 x 760 and cannot shrink below 560 x 480.

**App Store note.** `drawsBackground` is a private WebKit key. Tauri documents that private macOS API can make the Mac App Store reject an app, and this is the same key. It is set in one place (`shell.rs::prepare`); if review objects, the fallback is a rail beside the page for the floating button, which an earlier version of this change had.

**Gestures and shortcuts.**

| Input | What it does | Where |
|-------|--------------|-------|
| Two-finger swipe, in a page | Back and forward through the page's history | `WKWebView.allowsBackForwardNavigationGestures`, set when a view is built |
| Pinch, or two-finger double-tap, in a page | Zoom, as in Safari | `WKWebView.allowsMagnification` |
| Two-finger swipe, on an app screen (Settings, History, Usage) | Closes it (Back) | `useTrackpadSwipeBack`: wheel events, because the shell has no swipe event; right-to-left locales swipe the other way |
| Any bound key | Runs the action it is bound to (about 70 actions: navigation, tabs, page, scrolling, tools) | `useDesktopInput` and `src/features/keybindings/` |
| Escape | Closes the sheet or the fan, as Back does on mobile (the default for *Close what is open*) | `view.close` |

**Keyboard shortcuts.** Settings > *Keyboard shortcuts* (desktop only) lists every action and lets any of them be bound to any keys: one chord (`Mod+Shift+t`) or a sequence (`g g`, `Ctrl+x Ctrl+f`). `Mod` is Cmd on a Mac and Ctrl elsewhere. A key set is the base: *Standard* (browser keys), *Vim* (`j k h l`, `gg`, `G`, `d u`, `H L`, `/ n N`, `o t x`, `g t`, `:`, counts like `5j`) and *Emacs* (`C-n C-p`, `M-v`, `C-x C-f`, `C-x b`, `C-x k`, `C-s`, `M-x`); a person's own bindings replace an action's keys and win over the set. They live in `localStorage` (`om.keybindings`); the page has an off switch, after which only Escape still works. `Mod+Shift+P` (or `M-x`, `:`) opens a palette that lists every action by name.

**Floating button off (desktop).** Settings > Controls > *Floating button* hides the button for people who work by keys alone (`showFab` in the same `om.keybindings` entry; the action `app.fab`, `Mod+Shift+F`, toggles it and the palette lists it). It only stays hidden while keyboard shortcuts are on: turning shortcuts off shows it again, and the switch cannot hide it while no key is bound to Settings, the palette or the toggle. The way back: the switch in Settings, the shortcut, the palette, and the native menu bar, which lists every bound key.

**Settings on desktop.** `Screen` switches layout by the `desktop` flag (also written to `<html data-desktop>`, which the Tailwind `desktop:` variant reads): a compact title bar with the `Esc` key, a centered column, and on Settings a sidebar of parts (`SettingsNav`: General, Browsing, Controls, Sites and recipes, Incognito, AI assistant, Data). Phones get the same parts as a row of chips above the list. Pickers open as a centered dialog instead of a bottom sheet.

**Windows (desktop window manager).** Pages can be tiled side by side. The layout is a binary tree of splits whose leaves are open sessions (`src/features/tiling/layout.ts`, pure and tested); the shell keeps it in the app store (`layout`, null while one page fills the area) and the pane being in front is always `activeId`. `TileLayer` computes each window's rectangle from the page area, sends them with the plugin command `set_layout` (`Siteview::set_layout`: `State::panes`, shown by `sync_views` at each rectangle, every other session hidden; an empty list is no layout), and draws what the shell owns: a title strip above each window (click to bring to front, drag to move, button to close), a handle in each gap (drag to resize, double-click to even out), a mark on the window in front, and the drop highlight.

- **Drop to add.** Dragging a favorite out of the floating button's dial (outward from the dial; or sliding on past it with the finger still down) or out of a folder popup carries it over the page; the drop surface is a shell region over the whole page area (on Windows and Linux the pages step aside for it, as for any big overlay). The window under the pointer is split by where in it the pointer is (outer quarter: that side, taking half of it; middle: the page replaces the window's page). An empty tab opens the dropped page alone. An open page dragged by its title strip or as a tab moves instead of appearing twice. Escape cancels. Dropping a page `place`s it (`layout.ts`): a page opened without a drop (favorite, typed address, tab switch) takes the window in front, so the app behaves as before while no layout exists.
- **Keys and the palette.** The `Windows` action group: `tile.add{Right,Left,Below,Above}` open the palette's second list (favorites, open pages, a typed address) and put the choice on that side; `tile.focus*`, `tile.move*` (swap), `tile.grow`/`shrink`/`equalize`, `tile.close`, `tile.only`, `tile.saveFolder`. Changing the layout: `tile.flip` turns the split that holds the window in front (side by side becomes stacked, and back), `tile.arrangeRow` / `arrangeColumn` / `arrangeGrid` lay every window out again in order. Standard: `Mod+\`, `Mod+Shift+\`, `Mod+Alt+\`, `Mod+Alt+Shift+\` add; `Mod+Alt+Shift+Arrow` focus; `Mod+Alt+[` / `]` resize; `Mod+Alt+=` equalize; `Mod+Alt+/` flip; `Mod+Alt+1` / `2` / `3` row, column, grid; `Mod+Alt+W` close; `Mod+Alt+O` keep only. Vim: `Ctrl+w` then `h j k l`, `w`, `v`, `s`, `q`, `o`, `x` (flip), `=`, `+`, `-`, capitals to move. Emacs: `C-x o`, `C-x 3`, `C-x 2`, `C-x 0`, `C-x 1`.
- **Folders are layouts.** A favorites folder may carry a `layout` (`Folder.layout` in `library.rs`, type `Tiles` in `src-tauri/src/tiles.rs`: 2 to 8 web addresses, split ratios in 0.05 to 0.95, validated by `set_folders`). Each window is a favorite of the folder by its `url`. Dragging a whole folder out of the dial onto the page (or *Open all in windows* in the folder's popup) starts over with the folder's favorites in that layout (`openFolder`, `tilesForFolder` in `layout.ts`): a window whose favorite left the folder goes, a favorite added since joins on the right, and a folder with no usable layout opens a default one (two side by side; three a main window and a stack; four a grid; more balanced, at most eight). Live pages are reused, new sessions open the rest (`SessionAction` `openAll`). Opening the folder from the dial and dragging one favorite out works like any site. *Save the windows as a folder* (`tile.saveFolder`) makes a favorite of each window's page that is not one yet, files them in the named folder and stores the arrangement; renaming a folder keeps its layout. Not saved while incognito.
- **Sessions.** Every window is an open session, so the sweep (`sessionsToClose`) never closes one that is on screen, and closing a window closes its session; *Keep only this window* drops the layout and leaves the other pages open as tabs. A page that fails to open gives the window back to the page it replaced.
- **Focus.** On macOS the plugin's poller asks each window's `WKWebView` whether the window's first responder is in it (`platform::has_keyboard`) and, when a click moved it, makes that window the one in front and sends `siteview:focus`. Windows and Linux cannot say where the keyboard is, so there a click on a window's title strip (or the focus keys) brings it to the front; a click inside the page does not.
- **Not on mobile.** `set_layout` returns `DesktopOnly` on iOS and Android, which never call it.
The page view takes key presses before the shell sees them, so a binding reaches the page in front two ways:

- **Chords with the command key (or a function key)** become native menu items. The shell sends the list with `set_menu_shortcuts` whenever the bindings change; each item that is chosen comes back as `menu:action` and the shell runs the action. These work with the page focused. The shell also sees the same key press when it has the keyboard, so the same action from the menu and the keyboard within 120 ms runs once. Bare keys and Ctrl chords on a Mac are not menu items: they would break typing in the page's own fields.
- **Everything else** (Vim keys, sequences, Emacs `Ctrl` chords on a Mac) works while the shell has the keyboard: with a sheet open, on the start screen, or after *Switch between the page and shortcuts* (`Mod+;`), which calls `focus_keyboard` (`Siteview::focus_keyboard`). *Type in the page* (`i` in Vim) hands the keyboard back. With the shell focused, scrolling runs `page_scroll`: a fixed script through the Rust-only `evaluate` (`src/page_scroll.js`) that scrolls the scroller under the middle of the page; no site gets a channel or an extra script.

Reserved: Cmd/Ctrl with C, V, X, A, Z, Q, H, M, W belong to the system menu and text fields and cannot be bound as single chords. The menu labels and action names are English; only the page's chrome strings are translated.

**State.** Tauri has no navigation-state API. A poll thread (400 ms) reads URL, title, loading, back and forward from each session's `WKWebView` (`native.rs`) and emits `siteview:state` when something changed, the same event and payload as mobile. `painted` is true once a load has finished or 1.5 s have passed. Single-page navigations are caught by the poll, not by a load event.

**Sessions and profiles.** One child webview per session, all but the active one hidden. Each gets its own label (`site-<session>-<n>`) and a data store per profile (`data_store_identifier`), which is why the bundle requires macOS 14.

**Page script.** The recipe script is the webview's `initialization_script` (main frame, document start). A webview cannot swap it, so changing a site option rebuilds the visible page at its current address (its back/forward history is lost) and hidden sessions when next shown.

**Ad blocking.** The same WebKit rule lists as iOS, attached to the webview's `WKUserContentController`. Lists already in WebKit's store attach as soon as the lookup answers; missing ones are compiled in the background. The first request of a page opened right after the lists change may go out unblocked.

**Downloads.** A download link saves to the Downloads folder (WebKit picks a free file name) and the file is selected in Finder when it is complete. These WebKit downloads are separate from the app's own manager ([Downloads](./downloads.md)), which lists, pauses and resumes the files the user picks from the page or adds by address.

**Favicons.** Fetched from the site itself with `ureq` (the page's HTML for `<link rel="...icon">`, then `/apple-touch-icon.png` and `/favicon.ico`), staying inside the page's registrable domain, at most 400 kB each, decoded with the `image` crate (PNG, ICO, JPEG, GIF, WebP) and redrawn as a 96 px PNG `data:` URL. Nothing goes to an icon service.

**Owner check.** `LAContext` with `deviceOwnerAuthentication`: Touch ID or Apple Watch, with the account password as the system's own fallback. A Mac with neither a password nor Touch ID fails closed (`OwnerCheckUnavailable`). Rust-only, like on iOS, so no webview can raise or answer it. This is what lets incognito be entered.

**Notifications.** `UNUserNotificationCenter`, with the session id as the request identifier; tapping one reports the session as `siteview:notification-tap`. The center only exists for an app running from its `.app` bundle, so a development binary (`yarn dev:desktop`) returns `NotBundled`, and macOS only accepts requests from a properly signed app (see below).

**Purchases.** RevenueCat over StoreKit 2, as on iOS, in a Swift package (`tauri-plugin-billing/macos`, linked by `build.rs` through `swift-rs`) because Tauri's Swift plugin API is iOS-only. Rust calls three C functions (`src/macos.rs`): a blocking request that answers with JSON, a free, and a listener for entitlement changes. The macOS app is the same App Store app as the iPhone one, so it uses `OPENMEDIA_RC_KEY_IOS` unless `OPENMEDIA_RC_KEY_MACOS` is set. The Pro gate is therefore live on the Mac: `Entitlement::from_build` no longer forces Pro on macOS. It still does on Windows and Linux, which have no store. In a debug build `OPENMEDIA_DEV_ENTITLEMENT=pro|free` forces the answer. Purchases need an app signed for the Mac App Store, and RevenueCat needs a Mac App Store app (or the shared Apple app) with the three products; neither exists in this repository's setup.

**Navigation.** Only `http`, `https` and `about:` load; other schemes are refused. Tauri's navigation callback carries no frame information, so desktop cannot pin the main frame to its domain the way mobile does: a link in the page may leave the site, and the session's `scope` follows the page's registrable domain. This is deliberate for now: pinning would also send OAuth redirects (Google, Apple sign-in) out of the session. `target=_blank` and `window.open` are handled: a link inside the scope loads in place, one outside it opens in a popup window inside the app (`open_popup` in `desktop/mod.rs`), built on the opener's web view configuration so it shares the data store and `window.opener`, which a sign-in popup reports back through. It falls back to the default browser if the window cannot be built. The popup shares the opener's `WKUserContentController`, and wry skips a popup's own initialization scripts for that reason, so the `window.close()` shim (WebKit does not report that call to the app: it navigates to a refused address the popup closes on) is injected with every site view's scripts instead.

**User agent.** Safari's, without which Google refuses to sign in from an embedded view.

**Not on macOS.** A page-to-Core bridge (nothing uses it yet), `siteview:closed` when a web process dies and `siteview:memory` (Tauri exposes neither), JavaScript `alert`, `confirm` and `prompt` (wry has no handler, so WebKit ignores them), and the native in-app popup browser mobile uses for off-site links.

**Isolation.** Tauri injects `window.__TAURI_INTERNALS__` into every webview, so a page can see it, but every command is refused: the page is a remote origin and the only capability (`capabilities/default.json`) names the `main` webview, not the window. Page calls to `get_state`, `plugin:siteview|reload` and `plugin:event|listen` were rejected ("not allowed on window main, webview site-..."); a raw `ipc://` request was rejected for lack of an invoke key.

**Verified.** Debug builds on one Mac (macOS 26, Apple Silicon), with a local fixture server and a temporary scripted driver (removed afterwards), by window screenshots and the shell's own state readout:

- Pages load under the title bar, and the shell's controls line up with them. `siteview:state` reports title, URL, `loading`, `painted` and `scope`.
- `navigate`, then the Back menu item, leaves back disabled and forward enabled with no new request; Forward returns. Reload makes a new request. Zoom In twice changed `devicePixelRatio` from 2 to 2.42 and Actual Size restored 2. A second session opens and `activate` returns to the first.
- Open Address, Settings and the Escape key: the menu items open the sheets and Escape closes them (the keyboard goes to the shell while a sheet is open).
- Overlay: with a page loaded, the floating button draws over the full-window page with its glass look and no bar beside the page. A hit test at the button's region returns the shell view; a test at the page centre and at the page's top-left returns the page view. Real mouse clicks on the page were not driven (a window manager kept the test window off screen).
- `setColorScheme("light")` flipped `prefers-color-scheme` at the time of this run; on iOS and Android it no longer reaches pages (see [Dark Mode for Pages](./dark-mode.md)). Toggling a site option rebuilds the page at the same address with ad blocking still attached; a `fetch` to `www.google-analytics.com` (in the bundled lists) was blocked while one to `example.com` was not.
- Both gesture flags read back `true` from the `WKWebView`. A download of a 2048-byte attachment arrived in the Downloads folder.
- Favicons: `github.com` and `wikipedia.org` returned icons (17 and 2 kB as `data:` URLs); `example.com` has none and returned nothing.
- The user agent carries `Version/` and `Safari/`, and page-side IPC calls are refused, as above.
- A debug `.app` bundle launches with the notification delegate installed and `notify` returns `Ok`.

**Not verified.**

- Real trackpad gestures: the two-finger swipe and the pinch were never performed by a finger, only the settings that enable them were read back. The Settings swipe's wheel logic is unit-tested, not driven.
- Notifications: `usernotificationsd` rejected the debug bundle ("Entitlement `com.apple.private.usernotifications.bundle-identifiers` required"), because it is ad-hoc signed. No banner was seen and no tap was tried; a Developer ID or App Store signed build is needed to check.
- Touch ID: the prompt was never raised.
- macOS 14 and 15, Intel, a release build, two profiles with separate cookies, Google sign-in, `target=_blank` routing, resize and multiple displays beyond a resize by hand, a page covered by an overlay and a docked panel at once, video and fullscreen, and Windows and Linux (see [The Windows and Linux site view](#the-windows-and-linux-site-view)).

## The Windows and Linux site view

> **Status: Implemented, compiled, never run.** `cargo check` passes for the plugin and the app crate on `x86_64-pc-windows-gnu` and for the plugin on Linux (aarch64, in a Debian container); the unit tests for the layout helper pass. No Windows or Linux machine has opened a page with it. Treat everything below as intent until someone does.

The same module as the Mac (`desktop/mod.rs`): one Tauri child webview per session, the same `siteview:state` poller, popup, download and permission handling. `desktop/platform/` holds what differs.

**Click-through is the difference.** macOS keeps the shell transparent above the page and filters its clicks natively. WebView2 and WebKitGTK have no per-pixel click-through, so here the page sits above the shell and the shell is kept clear of it:

- `layout::fit_page` trims the page rectangle around the regions the shell reports (`data-hit`): each control that touches the page is cleared by cutting the one side that costs the least page. A control that would cost more than 60% of the page in either direction stays under the page.
- While an overlay (a region spanning at least 60% of the page in both directions: Settings, the command bar, the fan's backdrop) is open, or the shell covers the page with a page of its own, the page view is hidden and the shell shows through.
- Cost: the floating button takes a strip of the page beside it instead of floating over it.

**Windows.** Page history (`CanGoBack`, `CanGoForward`, `GoBack`, `GoForward`) comes from `ICoreWebView2` through `webview2-com`; the address from Tauri, the title and loading flag from the page callbacks. A profile is a WebView2 data folder. The owner check is Windows Hello (`UserConsentVerifier`, through the interop interface with the main window).

**Linux.** Tauri packs every web view of a window into one vertical box and ignores their positions, so `platform/linux.rs` moves the shell's `WebKitWebView` into a `GtkOverlay` with a `GtkFixed` layer on top (empty areas let clicks through) and moves each page view into that layer at the rectangle it is given. The owner check runs `pkexec true`, PolicyKit's own prompt (an administrator's password); a system without `pkexec` fails closed.

**Gaps, all on Windows and Linux:**

- Network request blocking (the Safari content rule lists) is not applied; cosmetic and scriptlet rules are.
- A media pause stops the page's own document; media in iframes of other origins keeps playing while the page is hidden.
- A changed document-start script rebuilds the page's view (the page reloads); the Mac swaps the script in place.
- No notifications for hidden sessions; `notify` returns `DesktopUnsupported`.
- Picture-in-picture and trackpad gestures are left to the web view.
- The page's pixel color is not sampled; the page script's own color is used.

## Known platform constraints

- **Android emulator drawing.** On the Android Emulator (API 37 image, System WebView 145, SwiftShader GL) with the default OpenGL HWUI pipeline, the transparent shell leaves stale rectangles on screen while the fan opens: missing items, a band of the page that is not dimmed, grey squares around the button, a ghost copy of the button. The shell's own compositor is right (a DevTools screenshot of it is clean), and the same app drawn with HWUI's Vulkan pipeline is clean, so this is the emulator's OpenGL path, not the layout. Run `adb shell setprop debug.hwui.renderer skiavk` and restart the app to look at the real UI (the property is lost at emulator reboot). Software layers (`LAYER_TYPE_SOFTWARE`) hide it too but scale the shell's drawing about 4% vertically, so touches miss what is drawn; a hardware layer, a per-frame `invalidate()`, turning HWUI partial updates off and turning CSS transitions off did not change it. Real devices are not checked.
- **Android late injection.** Without document-start-script support, injection can run after page scripts. CSS-first rules flash briefly; mitigated by hiding the view until the first inject, and by feature-detecting support (most current WebViews support it).
- **iOS WKWebView isolation.** `WKWebsiteDataStore(forIdentifier:)` requires iOS 17+. Older targets get a single shared store (one profile) unless a fallback is found.
- **Web versions are not native apps.** Mobile web Instagram/Facebook lack features (SocialLite documents: posting, one-time-view DMs, sending video, poll stickers, some music). Our product inherits these limits; communicate them rather than promising parity.
- **No push notifications.** Push for a third-party site needs a server relaying APNs/FCM. Out of scope by design (no backend). What exists instead: unread badges and local notifications for quick-access sites ([UI Design](./ui-design.md#unread-badges-and-notifications)). Android notification code exists but is not device-verified.
- **Cannot modify native apps.** iOS forbids altering other apps; Android can only via Accessibility Service (SocialLite's approach). We do neither: we replace the native app with the customized web view. A shell shortcut/URL-handler experience is a possible later step.
- **Background behavior.** A backgrounded site view may be suspended by the OS; do not rely on live observers while hidden.

## Small player (all platforms; the corner window is iOS)

The float button in the video controls (`video_controls.js`) lifts the video into a box in the bottom right corner (`data-openmedia-mini`): the element is moved, not copied, into a fixed box above the page with a close button and a play/pause button, leaving a comment marker where it was; closing, the video ending, or the site loading another source into the same element (`loadstart` with a new `currentSrc`) puts it back. Styles are applied with `!important` and re-applied if the site rewrites them. Pages in the box are not picture-in-picture: no system window is involved, so it is the same in the iOS Simulator and on a device.

iOS moves the whole page to the corner instead (`floatToCorner`): when the player goes up the page tells the app (`openmediaMini`, `{float: true}`), which keeps that page alive as it is, shows it as a small window in the corner above the shell (`placeCorner`), with `document[Symbol.for('openmedia.miniWindow')](true)` making its player fill the window, and opens the page before it (else the site's start page) in a fresh `WKWebView` in the session (`swapForFloatingVideo`, no history). Nothing in the kept page navigates, so a site that disposes its player when it navigates inside the page (YouTube; seen on the simulator: `emptied`, then the video removed from wherever it was) cannot take the video away, and the reader can go anywhere, in the fresh view or by the address bar. It is deliberately not the same page again: a second player of the same site starting made YouTube pause the first. The player ends when it is closed, when its video ends, or when its video is taken out of its box (a watchdog in the page; the page is torn down by `checkFloats`, every 2 s). A video playing in the fresh view does not close it; the two share the system's one audio, so the one started last pauses the other (the corner's play button starts it again). While the player is up the page is not suspended when the app is minimized. Not verified on a device. Drag in the corner window is not supported (the box moves only while it is over its own page).

Dragging the player down on a watch page (not a feed, where a swipe goes to the next video) does the same as the float button, with the box following the finger (`miniOn(video, from)` starts it at the video's rectangle, `miniDrag` interpolates to the corner); letting go short of 20 % of half the screen puts the video back. A watch page at its top sets `document[Symbol.for('openmedia.holdRefresh')]`, which the plugins' touch scripts read as "scrolled", so the app's pull to refresh does not take the drag (Android decides before the page hears of the touch).

Any page with a video over 15 % of the screen is a watch page (not only known paths). Players built as web components keep their video in a shadow root: `attachShadow` is wrapped once (roots are recorded, open or closed) and `allVideos()` searches them. A player in a frame (another site's, so out of reach) gets the controls through the copy of the script that runs in the frame (over 15 % of the screen only): it sends `om` messages to the page (`drag-start`, `drag-move`, `drag-end`, `float`, `unfloat`, `paused`), and the page answers (`drag-ok`, `mini`, `toggle`). The page moves the `iframe` element with `position: fixed` (a placeholder keeps its place; moving it in the DOM reloads it) and puts the buttons in a transparent box over it; only the page talks to the app. A frame measures its drag in screen coordinates, since it moves under the finger.

The corner window's expand button (`expandFromCorner`) puts the page back in front as it was: the page that took its place is disposed, the kept page returns to its place below the shell, and `miniClose` puts the video back where it was. The corner window is drawn non-opaque (the page rounds its own box); an opaque web view showed white corners. The small player does not open a system picture-in-picture window when the app is minimized. Drag in the corner window is not supported (the box moves only while it is over its own page).

Separately, leaving the app opens a real picture-in-picture window for the playing video (`enterPictureInPicture`, `floatForNavigationScript`). The guard script (`pictureInPictureGuardScript`) keeps other sites' videos from offering it.
